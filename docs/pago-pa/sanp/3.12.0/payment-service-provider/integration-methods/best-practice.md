# Best practice

## Payment Token <a href="#payment-token" id="payment-token"></a>

The use of the _payment token_ has the following two objectives:

1. to define a payment session in time;
2. to have an identifier generated by the pagoPA platform that allows for the end-to-end identification of a payment session.

The default duration of the _payment token_ is a common configuration for the entire pagoPA platform and cannot exceed 30 minutes. This parameter can be overwritten by the PSP with a value of less than 30 minutes, using the _expireTime_ field in the [activatePaymentNotice](../../appendix/Primitives/psp/soap-api.md#activatepaymentnotice-1) _request_. The value must be expressed in milliseconds.

It is essential that each PSP identifies the best token expiration value for the type of channel where the user goes to pay the notice.

The default duration of the _payment token_ may be redefined based on monitoring results; the update will be communicated through the publication of a minor version of this document.

The _payment token_ is provided in the _response_ from the pagoPA platform to an [activatePaymentNotice](../../appendix/Primitives/psp/soap-api.md#activatepaymentnotice-1). It must be included by the PSP in the _request_ to the [sendPaymentOutcome](../../appendix/Primitives/psp/soap-api.md#sendpaymentoutcome) and takes on the meaning of _identificativoUnivocoRiscossione_ in the Reporting Flows.

For the correct management of each payment session, every [activatePaymentNotice](../../appendix/Primitives/psp/soap-api.md#activatepaymentnotice-1) must always be followed by a [sendPaymentOutcome](../../appendix/Primitives/psp/soap-api.md#sendpaymentoutcome) for both OK and KO cases, in real-time with respect to the user's actions at the PSP's touchpoint. This is crucial for managing good service quality throughout the entire process.

After receiving a response from the Node, the [sendPaymentOutcome](../../appendix/Primitives/psp/soap-api.md#sendpaymentoutcome) must not be invoked again. To handle cases where a response is not received, you must use the [#idempotency-key](best-practice.md#idempotency-key "mention")

## sendPaymentOutcome After Payment Token Expiration <a href="#sendpaymentoutcome-after-payment-token-expiration" id="sendpaymentoutcome-after-payment-token-expiration"></a>

Only due to technical exceptions is the [sendPaymentOutcome](../../appendix/Primitives/psp/soap-api.md#sendpaymentoutcome) not received by the platform at the same time as the payment; therefore, if sent after the _payment token_ has expired, it is possible to encounter the cases identified by the following responses from the pagoPA platform

| Platform response                                                                       | Meaning                                                                                                                                                                      |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OK**                                                                                  | The payment outcome notification occurred before the token expired.                                                                                          |
| **PPT_TOKEN_SCADUTO**                         | The payment outcome notification occurred after the token expired, and the platform is unaware of any concurrent payments.                                   |
| **PPT_TOKEN_SCADUTO_KO** | The KO payment outcome notification occurred after the token expired. In this case, the Node does not check the status of the debt position. |
| **PPT_PAGAMENTO_DUPLICATO**                   | The payment outcome notification occurred after the token expired, and the platform detected another payment for the same position.                          |

For the **OK** case, no corrective action is necessary.

For the **PPT_PAGAMENTO_DUPLICATO** case, the correct action for the PSP is to refund the sum to the user.

For the **PPT_TOKEN_SCADUTO** error, the actions to be taken by the PSP are different depending on the case:

- in case of [pagamento-presso-frontend-dellec.md](../../casi-duso/pagamento-presso-frontend-dellec.md "mention") or[pagamento-da-touchpoint-pagopa](../../casi-duso/pagamento-da-touchpoint-pagopa/ "mention"), the error indicates that the payment was not successful, and the correct action for the PSP is to refund the sum to the user;
- in case of [pagamento-di-un-avviso-presso-psp.md](../../casi-duso/pagamento-di-un-avviso-presso-psp.md "mention"), the platform is unable to detect any concurrent payments, and the correct action for the PSP is to report the payment to the EC with _code 9_. If the payment process was managed in [stand-in.md](../../specifiche-attuative-del-nodo-dei-pagamenti-spc/funzionamento-generale/stand-in.md "mention") mode, _code 8_ must be used

In the case of **PPT_TOKEN_SCADUTO_KO**, the corrective action to be taken by the PSP is to manage the flow in a way that is temporally compatible with the duration of the _payment token_.

### sendPaymentOutcome OK

Following an **OK** result for the [sendPaymentOutcome ](../../appendix/Primitives/psp/soap-api.md#sendpaymentoutcome), the PSP is required to specify the following fields, which are therefore mandatory in case of a positive response:

- `paymentMethod`: specifies the payment method used;
- `fee`: indicates the amount of the commission paid in euros;
- `entityUniqueIdentifierType`: identifies the type of the person making the payment (**G** or **F**);
- `entityUniqueIdentifierValue`: indicates the tax code or VAT number of the person making the payment. If these are not available, it is possible to use 'ANONYMOUS';
- `fullName`: full name of the payer;
- `applicationDate`: application date of the payment;
- `transferDate`: date of transfer to the EC.

## Idempotency Key

The _idempotency key_ can be generated by the PSP for the following calls:

- [activatePaymentNotice](../../appendix/Primitives/psp/soap-api.md#activatepaymentnotice-1)
- [sendPaymentOutcome](../../appendix/Primitives/psp/soap-api.md#sendpaymentoutcome)

The purpose of the _idempotency key_ is to allow a call to be invoked multiple times without having _side effects_ on the payment status. The inclusion of the _idempotency key_ in the _requests_ of calls that handle it is **mandatory**. The use of this tool is limited to cases where a response to an idempotent call has not been received, for whatever reason.

Under no circumstances should the concept of payment session management be associated with the _idempotency key_; this must instead be handled through the correct use of the _payment token_

If a PSP, for example, does not receive the _response_ to the payment activation, it can make the same call again, taking care to use the same idempotency key, thereby obtaining the data that was intended for it during the first call. If it did not use the same idempotency key, it would instead receive a “payment in progress” _response_ and would not be able to proceed with the payment.

The generation rule for the _idempotency key_ is _`<CF\_PSP>` + "_" + `<RANDOM STRING>`_.

The duration of the _idempotency key_ is set by the pagoPA platform based on a common configuration for all PSPs. In the case of [activatePaymentNotice](../../appendix/Primitives/psp/soap-api.md#activatepaymentnotice-1), the maximum duration cannot exceed that of the _payment token._

In the case of [activatePaymentNotice](../../appendix/Primitives/psp/soap-api.md#activatepaymentnotice-1), the _idempotency key_ must be invalidated not only upon its own expiration but also upon receiving an outcome for the _payment token_ generated during activation.

Once expired, the _idempotency key_ becomes reusable.

The platform verifies the correct use of the _idempotency key_. In case of an error, the fault code _PPT_ERRORE_IDEMPOTENZA_ is returned. Input parameters are checked according to the table below.

| Idempotency Key                           | Other parameters                  | Action                                              |
| ----------------------------------------- | --------------------------------- | --------------------------------------------------- |
| Associable with an _original_ request     | Same as _original_ request        | No side effect + _original_ response                |
| Associable with an _original_ request     | Different from _original_ request | KO: improper use of idempotency key |
| Not associable with an _original_ request | Irrelevant                        | <p>This is effectively a new request<br></p>        |
